# Evidence, providers, accounts and security

## Canonical evidence
Preserve existing D1 aviation records, entities, identifiers, claims, source evidence, encounters, observations and original timestamps. A DOAA Encounter/Sighting is a real recorded electronic observation, **not** a flight, inferred route, archive lookup or human visual sighting. Distinguish source observation time from ingestion/receipt time; retain provider and retrieval provenance, raw values and conflicts. Never backfill historical identity using today's registration/operator without time-valid evidence. Unknown/null ≠ zero, no data ≠ no traffic, schedule ≠ observed movement, inferred ≠ verified. Do not create a synthetic journey by joining adjacent encounters or matching reused callsigns.

Live ADS-B acquisition uses a Render relay and multiple free provider fallbacks; Worker normalizes, bounds and checkpoints meaningful changes/heartbeat; D1 stores sampled history. Archive-based historical reconstruction is separately attributed and must not create DOAA encounters. Dossier reads must remain bounded and not unexpectedly consume metered provider quota. Metered AirLabs acquisition is optional, budgeted, failure-isolated and never a prerequisite for basic Inspector usefulness. Track, weather, airfield and media sources each need explicit rights, age and completeness.

## Authentication: explicit new decision, 2026-10-11
**Use username/password, not Google OAuth.** This supersedes the historical Google-only sign-in requirement. Existing password flow is a reuse candidate, not assumed production-verified. No anonymous application access or self-registration. Users remain signed in across normal visits and browser restarts, **without routine scheduled logout**; implement secure rolling/renewable server-side sessions or equivalent revocable persistent sessions, with documented absolute security limits only where necessary. Explicit **Sign out** must revoke the current session and clear the cookie. Disabling an account, resetting credentials and suspected compromise must support immediate server-side revocation. Secure HttpOnly SameSite cookies, TLS, CSRF/same-origin protection, rate limiting, strong password hashing, bounded input and no secret leakage are required.

An administrator (initially Brent) can create additional username/password accounts in the app, disable accounts, and securely reset credentials. Separate administrator and standard-user roles; enforce permissions server-side on every route. Do not put plaintext passwords in D1, logs, analytics, repository or URL. Never show existing passwords. Consider a one-time securely delivered temporary password or invitation with mandatory first-use change; exact onboarding flow may be selected during implementation. Do not expose public account creation. Each user's bookmarks, favorites and preferences are isolated by stable internal user ID; shared aviation evidence is accessible to authorized accounts. Preserve or safely map existing `password:<username>` subject-owned records without reassignment, leakage or deletion. Changing usernames must not orphan data.

## Verified source caveat / migration gate
Current `src/password-auth.mjs` queries `password_accounts`, and `migrations/0015_password_accounts.sql` **does** define that table; `0014_password_login_limits.sql` defines its throttle store. The older checked-in `scripts/preview-empty-schema.sql` stops at 0013 and therefore omits both tables. Actual production/preview migration application and account provisioning remain unverified. **Before implementing admin or testing authentication, verify whether migrations 0014–0015 have been applied in each environment without reading user records, update the reproducible empty-preview schema, and validate future additive migrations on an isolated empty DB.** No destructive migration, table rewrite, or production schema change without explicit review and backups.

Current password login sets a **seven-day** cookie/session; this must change. Existing `POST /auth/sign-out` deletes the token-hash session and clears cookie; reuse with UI and tests. Legacy OAuth code may be retired only after confirming no dependent data migration is needed. Avoid logging sensitive auth context.

## Preference semantics
Account-synchronized snapshot; last server-accepted complete snapshot wins, not per-field merges. Local changes apply immediately, with visible pending/failed sync and bounded retry. Bookmarks are references to immutable observed moments; do not conflate with inferred archive records. Personal records remain private across devices and accounts.

## Test requirements
Two distinct users plus administrator: forbidden cross-user GET/POST/DELETE; login throttling; wrong password; expiry/renewal; explicit logout; account disable and all-session revocation; password reset and forced change; concurrent preference snapshots; failed network save; unauthenticated API and asset access. Test zero/unknown, conflicting identity, missing provider, stale timestamps, archive provenance, and budget exhaustion. Do not run destructive tests against production.
